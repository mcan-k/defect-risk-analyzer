# Scoring snapshots — provenance

These two files are the only surviving evidence that the Faz 2 refactor preserved
scoring behaviour. `tests/test_scoring_regression.py` compares them against the
current `core/scoring.py` on every CI run.

Read this before changing anything here.

## Where they came from

| | |
|---|---|
| **Generated at commit** | `aff55c6` — the last state before the Faz 2 refactor |
| **Scoring code at that commit** | `src/defect_risk_analyzer/risk_analyzer.py` (751 lines) |
| **Input** | `data/sample_bugs.json`, 20 bugs across 6 components |
| **Generated by** | `tests/tools/make_baseline.py` |
| **Metadata recorded in each file** | `"_mode": "A"`, `"_scoring_module": "(none — RiskAnalyzer)"` |

`risk_analyzer.py` was **deleted in `2a52585`**, the Faz 2 merge, which added
`core/scoring.py` in its place. Nothing in the working tree computes these numbers
the way they were computed when they were captured.

## Why both clocks are kept

`calculate_module_stats` derives a 30-day trend window from `now`. The sample bugs
span 2025-12-15 to 2026-03-20, so the reference time decides which branches run:

- **`now2026-08-11`** — every bug is older than 30 days. Every module comes out
  `trend: "decreasing"` with `recent_bug_count: 0`.
- **`now2026-04-01`** — the window opens 2026-03-02, so March bugs count as recent.
  This is the **only** file that exercises the `increasing` and `stable` branches and
  the 1.3 / 1.0 trend multipliers: Authentication and Payment go `increasing`
  (79→100 and 55→90), Reporting goes `stable` (34→42).

Deleting either file silently drops coverage. Keep both.

## If the regression test fails

**Investigate the behaviour change in `core/scoring.py`. Do not regenerate or edit
these files.**

Updating a snapshot to match new output destroys the only proof that the refactor
was behaviour-preserving, and it does so quietly — the suite goes green and the
evidence is gone. A failure here means current scoring disagrees with the
pre-refactor implementation. That is either a real regression or a deliberate
change; both need a human decision, and a deliberate change needs its own record.

One clarification, because the tempting shortcut looks available: the deleted source
**is** still reachable from git history —

```bash
git show aff55c6:src/defect_risk_analyzer/risk_analyzer.py
```

That is how `baseline/compare_service.py` used to load it. Recovering it is possible;
doing so to re-bless a diff is the exact mistake this file exists to prevent.

## Regenerating (for a *future* refactor, not for these files)

`tests/tools/make_baseline.py` is preserved next to the fixtures it produced:

```bash
python tests/tools/make_baseline.py 2026-08-11T12:00:00
```

It snapshots **whatever scoring module is importable at the time**, so today it always
emits `"_mode": "B"`, `"_scoring_module": "defect_risk_analyzer.core.scoring"`. It
cannot reproduce the mode-A files above — that is the point of committing them.

Its use is to capture a before/after pair around a *new* refactor, the same way this
pair was captured around Faz 2. Output goes to the current working directory by
default (root-level `scores-*.json` is gitignored); pass a second argument for another
destination. Compare a pair by diffing the `modules` subtree and ignoring `_mode` and
`_scoring_module`, which is what the regression test does.

## Verified equivalence

The mode-A files here and the mode-B files captured after Faz 2 differ in **only**
those two metadata fields — the entire `modules` payload is byte-identical across all
six modules and both clocks. That equality is the result being preserved.
